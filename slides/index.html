AIAgent ResolveA2AAgent(string envVar, string cardPath = "/.well-known/agent-card.json")
{
    var url = Environment.GetEnvironmentVariable(envVar);

    var httpClient = new HttpClient { BaseAddress = new Uri(url) };
    var resolver = new A2ACardResolver(httpClient.BaseAddress!, httpClient, agentCardPath: cardPath);

    return resolver.GetAgentCardAsync().Result.AsAIAgent(httpClient);
}

Architecture evolution

From agent as a tool to agent as a skill

Keep domain services remote. Move instructions into the advisor. Tools stay tools.

We are changing the reasoning boundary, not replacing A2A universally. The skills provider has no specialist model loop. The advisor still uses multiple model iterations.

A small demo of a larger catalog

Four skills, twelve toolsselect a skill, expose its provider's complete tool group
Independent language choicesPython skills advisor; .NET MCP providers; no required language rewrite
Small real catalog?load provider tools upfront with the standard SDK
Progressive registrationnative MAF capability, not a Foundry Toolbox

For a small catalog, eager loading avoids the skill-to-provider hook entirely.

The original A2A advisor is .NET with Python and .NET specialists. Twelve tools do not inherently justify progressive loading. This simple resort illustrates a more complex catalog scenario. With eager tool exposure, skill instructions can still load on demand. These are alternative SDK compositions, not runtime compatibility modes in this demo.

Move instructions and reasoning, not business logic. Authentication and transport do not become prose.

The Agent Card's descriptive identity helps select a competence; other card fields remain infrastructure concerns. The former system prompt supplies domain rules and procedures. The actual generated SKILL.md adds MAF-specific tool-loading guidance, so it is not a verbatim host-neutral example. There is no model inside the four MCP providers. The researcher remains an agent tool.

    use_progressive_disclosure=False,

Keep native functions host-side. Register a provider's group only after its skill loads.

These are shortened configuration excerpts, not the complete shared builder. False disables native per-tool loading helpers; it does not expose all functions initially because these MCP objects are not registered in the agent's initial tools. A function-invocation hook uses public add_tools after a successful skill read. The configured providers' catalogs are authoritative, with no duplicate name list. MAF discovers paginated tools/list upfront. Initial context contains skill summaries/loading helpers, advisor instructions and the researcher. The trusted read-only provider tools use never_require; adding write tools requires reconsidering that policy. This SDK capability is not Foundry-only.

Select the skill, expose its tool group


load_skill({"skill_name":"weather"})
  -> native skill read succeeds
  -> host hook: add_tools(all weather functions)
  -> all 3 descriptions/schemas on NEXT model iteration

weather_weather_forecast({"hours":6})
  -> MCP tools/call: weather_forecast
  -> remote domain service returns structured data

The host chooses the group; the model chooses what to execute. Loading is not execution.

Each provider currently hosts one skill. A successful load_skill triggers our small skill-to-provider binding, not automatic behavior built into SkillsProvider. It registers that provider's full native catalog with FunctionInvocationContext.add_tools for the next iteration. All tool descriptions and input schemas are then available for operation selection; no separate loader model call is needed. Other providers remain hidden. Failed skill reads must not add tools. Prefixes isolate providers: the repeated weather_ is intentional. This is context exposure, not authorization; no custom operation dispatcher is involved.

Shared connections, request-local tools

Reusable MCP connectionsopen for app lifetime; AsyncExitStack handles cleanup
Per-invocation registrationstool groups stay out of other users' requests
Small integration hooksuccessful skill read maps to its configured provider catalog
SDK remains in controladd_tools, descriptions, schemas, MCP dispatch, approvals

Run ends: registrations disappear. Shared MCP connections and conversation history remain.

The native_mcp.py hook implements the skill-to-provider association through public APIs. MCP sessions and native catalog functions are app-owned; add_tools changes only the current run, not the shared agent or mutable loaded-name state. Registrations remain through streaming and are discarded on completion, failure or cancellation. Followups load their skills again. This does not send a remote unload command. Native never_require and automatic function invocation handle read-only provider operations. SkillsProvider's native disable_load_skill_approval and disable_read_skill_resource_approval settings make instruction reads automatic too, avoiding approval/resumption boundaries. There is no custom approval/resumption engine. For small catalogs, directly register all native MCP tools and omit the hook.
