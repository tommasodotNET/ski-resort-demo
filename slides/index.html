AIAgent ResolveA2AAgent(string envVar, string cardPath = "/.well-known/agent-card.json")
{
    var url = Environment.GetEnvironmentVariable(envVar);

    var httpClient = new HttpClient { BaseAddress = new Uri(url) };
    var resolver = new A2ACardResolver(httpClient.BaseAddress!, httpClient, agentCardPath: cardPath);

    return resolver.GetAgentCardAsync().Result.AsAIAgent(httpClient);
}

Architecture evolution

From agent as a tool to agent as a skill

Keep domain services remote. Move instructions into the advisor. Tools stay tools.

We are changing the reasoning boundary, not replacing A2A universally. The skills provider has no specialist model loop. The advisor still uses multiple model iterations.

A small demo of a larger catalog

Four skills, twelve toolsillustrate how procedures guide on-demand schema exposure
Independent language choicesPython skills advisor; .NET MCP providers; no required language rewrite
Small real catalog?load provider tools upfront with the standard SDK
Progressive registrationnative MAF capability, not a Foundry Toolbox

Eager tool loading avoids the progressive-state lifecycle middleware entirely.

The original A2A advisor is .NET with Python and .NET specialists. Twelve tools do not inherently justify progressive loading. This simple resort illustrates a more complex catalog scenario. With eager tool exposure, skill instructions can still load on demand. These are alternative SDK compositions, not runtime compatibility modes in this demo.

Same domain boundary, different runtime

Move instructions and reasoning, not business logic. Authentication and transport do not become prose.

The Agent Card's descriptive identity helps select a competence; other card fields remain infrastructure concerns. The former system prompt supplies domain rules and procedures. The actual generated SKILL.md adds MAF-specific tool-loading guidance, so it is not a verbatim host-neutral example. There is no model inside the four MCP providers. The researcher remains an agent tool.

Host discovers the catalog upfront. The model sees operation schemas only when loaded.

These are shortened configuration excerpts, not the complete shared builder. The configured providers' catalogs are authoritative; there is no duplicate tool-name list in the advisor. Every advertised tool is eligible for loading, not automatically exposed in initial context. The trusted providers currently publish read-only operations; never_require is a separate host policy that must be revisited if write tools are added. MAF retrieves paginated tools/list before the first model iteration. Initial context includes skill summaries and native management functions, plus advisor instructions and the researcher tool. list_mcp_tools can reveal the provider catalog; named loading avoids that extra listing. This SDK function-calling feature is not Foundry-only.

The model makes the association


load_skill({"skill_name":"weather"})
  -> instructions list relevant exact tool names

weather_load_tool({"tool":"weather_forecast"})
  -> MAF registers schema for NEXT model iteration

weather_weather_forecast({"hours":6})
  -> MCP tools/call: weather_forecast
  -> remote domain service returns structured data

Skill loading is guidance, not authorization or atomic tool-dependency resolution.

Native load_skill returns instructions. The LLM chooses a name and calls the native loader separately. The SDK adds the function through FunctionInvocationContext.add_tools for the next iteration. The direct function retains native MCP transport and approval behavior. Prefixes isolate providers: the repeated weather_ is intentional. A model can load tools without first loading a skill. No custom operation dispatcher is involved.

Native loading, small lifetime adapter

Reusable MCP connectionsopen for app lifetime; AsyncExitStack handles cleanup
Per-invocation tool objectsisolate mutable loaded-name state on shared-agent hosts
Small public-API adapterNativeMCPToolsMiddleware supplies runtime objects and stream lifetime
SDK remains in controldiscovery, dynamic loading, schemas, dispatch, approvals

The middleware scopes objects. It does not map a skill to tools or load the chosen operations.

The native_mcp.py adapter is under 100 lines including documentation, imports and SkillConnection. Shared MCP sessions are distinct from invocation-local MCPStreamableHTTPTool objects. Those objects stay alive until a lazy stream completes, fails or is cancelled. Native approval_mode=never_require and the SDK function-calling loop execute provider operations automatically. Standard ToolApprovalMiddleware applies the SkillsProvider read-only auto-approval rule to instructional reads. There is no custom approval state or resumption logic. Ordinary followups reload operations. For small catalogs, direct eager SDK registration avoids this progressive-state adapter. Do not describe the implementation as zero custom code or say MAF cannot scope tools.

This is the same six-row evidence as BLOG_DISTRIBUTED_AGENT_SKILLS.md. Wall time runs from frontend POST to SSE body exhaustion, not first token. All six requests used the exact displayed prompt with no previous response ID or history. Existing processes were reused. Total tokens across three runs: A2A 11,952; native 24,242. Native cached input totals 17,920 and is already included in input. A2A advisor cache is zero but specialist counters are absent, so whole-system cache is unknown. Do not infer a pure architectural speedup or twice the billable cost. Native consistently used four model calls: batched skill loads, batched native tool loads, batched direct tools, final answer. A2A used six, six and seven leaves including remote specialists. Pair 3 invoked the coach and asked for skill level, whereas native recommended a lift; pairs 1 and 2 A2A also requested forecasts. Native safety wording in pairs 2 and 3 was not backed by a safety-provider call. This is not an equal-quality controlled study. All responses completed without benchmark retries or failing model leaves; non-model A2A queue-shutdown spans remain in saved evidence. Aggregate invoke_agent/API usage is not added again.
