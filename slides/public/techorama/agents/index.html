Skills: what Aspire ships vs. what you add

Markdown instructions every coding agent understands. Frontmatter says when to use one; the body says how.

Tommaso’s slide (merged with “How do skills work?”). Skills are supported by all the major coding agents: Markdown files with instructions on how to use a tool like a CLI, or how to author code, with frontmatter that guides when the agent picks them up. Aspire ships a set via aspire agent init; the real leverage comes from adding your own for your app. Draft note from Tommaso’s version: refine with concrete examples from the demo app.

Part 2 · Build AI

Building agents with Microsoft Agent Framework

Agent Framework + Aspire, end to end

Hand-off to the Build AI half. We’ve seen a coding agent use Aspire; now we build the kind of agent your customers will talk to — and Aspire runs everything around it.

An agentic app is a distributed app

Models

Local or cloud deployments, keys and endpoints

Agents

One or many services, often in different languages

Tools and MCP

Servers and APIs your agents call to get work done

Memory

Vector stores, caches and databases for context

Frontends

The chat UI or app your users actually see

Telemetry

What did the model actually do, and why?

The key reframe: an “agent” is never just a prompt. It’s a model deployment, one or more agent services, tools and MCP servers, memory, a frontend, and telemetry so you can tell what happened. That’s a distributed app — exactly the thing Aspire was built to wrangle.

Microsoft Agent Framework

Open-source SDK for AI agents and multi-agent workflows. 1.0 for .NET and Python since April 2026; Go in preview.

Agents

Foundry, OpenAI, Anthropic, Ollama and more behind one API

Workflows

Graph-based: sequential, concurrent, handoff, group chat

Tools and MCP

Your own functions plus any MCP server, with middleware

Telemetry

OpenTelemetry GenAI traces and metrics for every call

The successor to Semantic Kernel and AutoGen, built by the same teams.

Tommaso’s slide. Agent Framework is the “what goes inside the agent service” piece: one agent abstraction across model providers, graph-based multi-agent workflows (sequential, concurrent, handoff, group chat, Magentic-One), tool calling and MCP. 1.0 shipped in April 2026 for .NET and Python with stable APIs; Go is in preview. The bit that matters for us: it emits OpenTelemetry spans (invoke_agent, chat, execute_tool) and token-usage metrics using the GenAI semantic conventions — and its own docs recommend the Aspire dashboard for local dev. In Python instrumentation is on by default; in .NET you add UseOpenTelemetry().

Deployment

Your agent is just another service, container and endpoint.

Why the two fit together. Agent Framework builds the agent; Aspire runs everything around it. Locally: swap between a local model and a provisioned one without touching the agent code. In the dashboard: Agent Framework’s OpenTelemetry shows up as GenAI spans — prompts, tool calls, token counts. At deploy time: the agent is treated like any other resource in the AppHost.

Modeling an agentic app in the AppHost

apphost.ts

AI model

Agent + frontend

const foundry = await builder.addFoundry("foundry");

const chat = foundry.addDeployment("chatmodel", FoundryModels.OpenAI.Gpt41);

const agent = await builder.addPythonApp("agent", "../agent", "main.py")

.withReference(chat);

await builder.addViteApp("frontend", "../frontend")

.withReference(agent);

Connect with references, not hand-wired config — same path from local dev to deployment.

Tommaso’s “Modeling an agentic app” points, merged here: an agent app is a distributed app, so declare each part as a resource — Agent Framework services, model endpoints, MCP servers and tools, plus a vector store or database and a frontend chat UI. Connect them with references, not hand-wired config: endpoints, connection strings and keys flow from the AppHost, and the same app model runs locally and drives deployment. The whole agentic app in a handful of lines: a model deployment, an Agent Framework service that references it, and a frontend that references the agent. Aspire injects the endpoint and credentials, so the agent code never hard-codes a key. CHECK BEFORE THE TALK: match this snippet to the exact APIs and languages in the demo repo.

Deployment targets in the AppHost

01

Resources are private by default

The AppHost is its own private network. Nothing is reachable from outside until you mark a resource with WithExternalHttpEndpoints(), explicitly, per resource.

02

Add a deployment integration

The easiest way to test locally is Docker Compose (Aspire.Hosting.Docker), but the model is the same for a managed cloud.

03

Tweak it from code

Amend or override the Docker Compose file Aspire generates from your AppHost.

.ConfigureComposeFile(

compose => { ... });

Multiple deployment targets are supported — resources can be assigned to different ones.

Tommaso’s slide. Three things to know before you ship: resources are private unless you opt in with WithExternalHttpEndpoints(); add a deployment integration — Docker Compose is the easiest to try locally, and the model is the same for a managed cloud; and you can still tweak the generated output from code. You can also mix targets, assigning different resources to different environments.
